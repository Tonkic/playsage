# 编写和维护项目文档

本规范适用于 PlaySage 的开发者、审阅者和文档同步 Agent。目标是让读者找到任务、完成操作，并知道当前限制。每次修改都在同一轮检查文档影响；没有文档影响时说明理由，不制造无意义的修改。

## 先确定事实和读者任务

以当前实现、配置及对应提交的实际验证结果为依据。提交说明只表达意图；测试名称不代表测试通过。发现实现、测试与文档冲突时报告具体出处，不替开发者猜测。

明确区分以下状态：

| 状态 | 使用条件 |
| --- | --- |
| 已实现 | 当前源码或配置提供该行为 |
| 已验证 | 有与当前提交及环境对应的实际检查结果 |
| 历史实测 | 保留原环境、版本和时间范围，不作为当前验收 |
| 未验证 | 缺少测试、实机或部署证据 |
| 计划 | 尚未交付，不使用表示已完成的措辞 |

离线测试不等于实机验收；命令退出成功不等于游戏目标完成。不能根据截图、模拟或规则匹配授予 `verified`、真实输入权限或无人值守重放权限。

## 使用直接、自然的语言

采用 Microsoft Writing Style Guide 的原则，并按中文阅读习惯组织内容：

- 开头交代可以完成什么、适用对象和重要限制。
- 使用主动、简洁的句子，一句表达一个主要意思。删除“值得注意的是”等无信息套话。
- 标题描述任务，例如“查看最近的操作证据”。同级标题保持一致的结构；英文标题使用句式大小写。
- 统一术语，必要术语首次出现时解释。路径、命令、参数和状态使用代码格式。
- 不使用“全面提升”“无缝支持”“智能赋能”等缺乏证据的宣传词。
- 不把 Agent 思考过程、工具调用流水账或内部排查过程放入用户指南。
- 做最小必要修改，不因局部行为变化重写整篇文档。

## 写出可执行的步骤

一个操作流程应包含以下信息：

1. 列出平台、权限、依赖等前提条件。
2. 指明执行位置，解释需要替换的占位值和合成示例。
3. 用编号步骤描述明确动作，每步优先完成一件事。
4. 给出预期结果和成功判断方式。
5. 将数据覆盖、真实输入、权限变更等风险提示放在危险操作之前。
6. 说明失败后检查什么、何时停止；不笼统建议重试。

验证示例时不得启动游戏、发送真实输入、动态执行活动包 Python、读取账户凭据或执行破坏性命令。仅做语法检查时，明确写为“语法检查”，不能写成操作成功。

## 将信息放在合适的位置

| 内容 | 负责的信息 |
| --- | --- |
| README | 用途、能力边界、快速开始和文档入口 |
| 使用指南 | 操作步骤、结果和故障处理 |
| 架构文档 | 组件职责、数据流、约束和设计理由 |
| 变更记录 | 影响用户的行为变化、兼容性和迁移要求 |
| Workflow 报告或 PR | 提交范围、修改理由、检查结果和证据缺口 |

仅修改测试或内部实现且不影响用户行为时，可以不改用户指南，但必须在本轮交付说明或 workflow 报告中记录检查范围、验证结果和无需修改的原因。

## 保留兼容标识和历史记录

当前名称使用 `playsage`、`playsage.*`、`playsage-event`、`playsage-skill-author` 和 `PlaySage.ChildSession`。旧 CLI 与导入转发、旧会话变量回退及历史记录按[改名与兼容说明](rename-playsage.md)保留。不要把兼容标识或历史证据误改为当前名称；新文档示例不得继续指向旧实现文件。

活动包、游戏知识包、历史实测报告、批准方案、运行证据、用户配置和数据不属于普通文档同步的写入范围。自动化不得为通过检查而改动源码、测试、依赖、工作流、安全检查程序或本规范。人工维护上述规则需单独审阅，不由文档 Agent 自我放宽。

## 同轮检查文档影响

1. 确定本轮基准与当前提交；本地未提交工作则明确说明检查的是工作区快照。
2. 阅读差异、相关实现、已有文档和实际验证证据。
3. 判断是否影响功能、命令、参数、格式、依赖、架构或安全边界。
4. 更新受影响的页面，或记录无需修改的具体原因。证据不足时标记受阻，不编造结论。
5. 检查本地链接、示例、术语和安全边界；报告实际运行的检查。

每次检查使用以下输出格式：

```text
检查范围：基准提交 → 当前提交（或明确标记的本地快照）
文档结果：已更新 / 无需修改 / 受阻
修改说明：哪些页面对应哪些行为变化，或无需修改的理由
验证与限制：实际检查、未验证内容、需人工确认事项
```

报告与具体提交或快照绑定。后续代码变化后必须重新检查，旧结果不能证明新提交已验收。自动化流程和部署限制见[准备文档同步工作流](documentation-workflow.md)。
